# Спецификация: сравнение больших таблиц по диапазонам и выравнивание дельты

## Задача (слова пользователя)

> «если таблица почти терабайт весит, как можно проверить так чтобы это быстро и эффективно и точно проверила ?»
> «все нужно автоматически проверить, это все для дельты нужно чтобы выровнить»

Сейчас на больших таблицах ломаются оба шага:
- **Сравнение.** Для каждой строки «ключ + md5» уходит во временную таблицу приёмника. На терабайте это сотни ГБ по сети и временная таблица того же размера.
- **Загрузка разницы.** Источник целиком копируется в staging.

## Решение

Режим «по диапазонам» включается автоматически:
1. Таблица режется на диапазоны значений одной колонки.
2. По каждому диапазону обе стороны считают контрольную сумму. Совпавшие диапазоны закрываются сразу.
3. Несовпавшие рекурсивно дробятся до «листа». В листе работает построчное сравнение (существующий `compare_table`), ограниченное предикатом диапазона.
4. Список несовпавших листьев сохраняется. Загрузка разницы для такой таблицы перекачивает и выравнивает только эти листья.

Итоговые числа — `src_rows`, `dst_rows`, `to_insert`, `to_update`, `to_delete` — точные и совпадают с тем, что дало бы построчное сравнение всей таблицы.

## Решения по реализации

1. **Порог.** Режим включается, если по статистике источника `pg_total_relation_size >= CHUNK_MIN_BYTES` (2 ГБ) **или** `reltuples >= CHUNK_MIN_ROWS` (5 млн). Оба значения — константы модуля. Ниже порога — как сейчас.

2. **Колонка нарезки** выбирается автоматически.
   - **Есть ключ** (pk / unique_index / sync_keys) — первая колонка ключа. Если ключ составной, предикат строится по первой колонке, а внутри диапазона сравнение идёт по полному ключу.
   - **Нет ключа** — колонка, которая есть в обеих таблицах с одинаковым типом. Предпочтение по типу:
     1. date / timestamp / timestamptz;
     2. целочисленная;
     3. numeric;
     4. text / uuid.

     Среди кандидатов — наибольший `n_distinct` по `pg_stats` источника.
   - **Подходящей колонки нет** — одна контрольная сумма на всю таблицу. Совпала — `same`; нет — прежнее построчное сравнение всей таблицы с пометкой в `message`.

3. **Границы.** Верхний уровень делится на `TOP_CHUNKS` диапазонов (64).
   - integer / numeric / date / timestamp — равные отрезки от min/max источника; min и max берутся через `ORDER BY col LIMIT 1` в обе стороны (по индексу, если он есть).
   - Прочие типы — квантили по выборке `TABLESAMPLE SYSTEM(p)`; `p` подбирается так, чтобы читать ~100 тыс. строк.
   - **Покрытие полное:**
     - первый диапазон `col < b1`;
     - последний `col >= bN`;
     - отдельный диапазон `col IS NULL`.

     Строки приёмника вне [min, max] источника тоже попадают в какой-то диапазон.
   - Если collation колонки на сторонах различается, предикаты для текста пишутся с `COLLATE "C"` на обеих сторонах; если одинаковая — без него.

4. **Контрольная сумма диапазона** — одинаковый запрос на каждой стороне:

   ```sql
   SELECT count(*),
          sum(('x'||substr(h,1,16))::bit(64)::bigint),
          sum(('x'||substr(h,17,16))::bit(64)::bigint)
   FROM (SELECT <row_hash_sql> AS h FROM t WHERE <pred>) s
   ```

   - `row_hash_sql` — тот же, что в построчном сравнении: по колонкам в отсортированном порядке.
   - Сессии нормализованы, как сейчас.
   - Диапазон совпал, если совпали все три значения.

5. **Дробление.** Несовпавший диапазон с `max(src_count, dst_count) > LEAF_ROWS` (100 тыс.) делится на `SPLIT_FANOUT` (16) поддиапазонов:
   - числа и даты — арифметически;
   - прочее — `percentile_disc` по источнику внутри диапазона;
   - если делить нельзя (одно значение колонки) — это лист.

   Остальные несовпавшие диапазоны — листья. Для листа вызывается `compare_table` с предикатом.

6. **`compare_table`** получает необязательный параметр `where` (Composable или None), обратно совместимо. Предикат применяется:
   - к выборке источника (`build_source_select`);
   - к стороне приёмника в подсчёте;
   - к проверке дублей приёмника.

7. **Параллельность.** Единица работы — «таблица» или «диапазон таблицы» в общей очереди воркеров; число воркеров — существующий `parallel` (1..8).
   - Каждая единица считается на паре соединений воркера.
   - Поддиапазоны кладутся в ту же очередь.
   - Таблица закрывается, когда закрыты все её диапазоны: итог суммируется в `pg_compare_results`, item → done.
   - Стоп работает как сейчас.

8. **Хранение.** Новая SQLite-таблица `pg_compare_ranges`, `CREATE TABLE IF NOT EXISTS` в `init_db`:

   | Колонка | Смысл |
   |---|---|
   | `id`, `job_id`, `schema_name`, `table_name` | привязка к задаче и таблице |
   | `column_name` | колонка нарезки |
   | `lo_json`, `hi_json` | границы текстом; null — открытая граница |
   | `is_null_range` | диапазон `col IS NULL` |
   | `depth` | глубина дробления |
   | `src_rows`, `dst_rows`, `to_insert`, `to_update`, `to_delete` | счётчики |
   | `status` | `same` / `differs` / `error` |

   - Пишутся только листья со статусом `differs`; совпавшие диапазоны не хранятся.
   - В `pg_compare_results`:
     - `message` — «по диапазонам: проверено N, несовпавших M»;
     - в ответе API — новое поле `chunked: {checked, total, mismatched}`.

9. **Загрузка разницы** (`pg_diff_load`, action `diff`). Если у сравнения есть листья `differs` для таблицы:
   - в staging копируются только строки источника `WHERE <предикат листа>` — по всем листьям;
   - UPDATE и INSERT — как сейчас (staging содержит только эти диапазоны);
   - DELETE (только при `delete_missing`) ограничен предикатами листьев: по листу, в той же транзакции;
   - без ключа: `INSERT … EXCEPT ALL` и удаление лишних копий — тоже в пределах предикатов листьев.

   Если листьев нет (таблица не большая) — прежнее поведение.

10. **Безопасность.**
    - Источник только читается.
    - Идентификаторы — через `sql.Identifier`.
    - Значения границ — только параметрами (`sql.Literal` / `%s`), без склейки строк.

## Границы и швы

| Модуль | Владеет | Выставляет |
|---|---|---|
| `modules/pg_ranges.py` (новый) | нарезка, предикаты, контрольные суммы, дробление | см. список ниже |
| `modules/pg_compare.py` | раннер, очередь единиц, итог по таблице | `compare_table(..., where=None)`; запись `pg_compare_ranges`; `get_mismatched_ranges(job_id, schema, table) -> [Range + column]` |
| `modules/pg_diff_load.py` | загрузка по листьям | использует `get_mismatched_ranges`, `range_predicate` |
| `static/js/pg_compare.js` | прогресс диапазонов | показывает `chunked` |

Интерфейс `pg_ranges`:
- `should_chunk(src_conn, schema, table) -> bool`
- `pick_chunk_column(src_conn, dst_conn, schema, table, key_columns) -> {name, kind}` или None
- `top_ranges(src_conn, schema, table, column) -> [Range]`
- `range_predicate(alias, column, rng, collate_c=False) -> Composable`
- `range_checksum(conn, schema, table, columns, pred) -> (count, s1, s2)`
- `split_range(src_conn, schema, table, column, rng) -> [Range]`
- `Range = {lo, hi, is_null, depth}`; `lo` и `hi` — значения Python или None.

**Швы для тестов:**
- чистые построители SQL в `pg_ranges`;
- раннер на фейках;
- живые тесты при заданных `PGCMP_LIVE_DSN_SRC` / `DST`.

## Проверка на живой базе

Временный PG 17, таблица ≥ 20 млн строк. Сравнение по диапазонам; порог для теста понижается через константу в тесте или скрипте. Ожидается:
- числа совпадают с построчным сравнением;
- загрузка разницы выравнивает приёмник;
- повторное сравнение даёт `same`;
- в staging попадают только строки несовпавших диапазонов.
