## Что должно заработать

`POST /api/pg/diff-load/start` запускает задачу `pg_diff_load`. Для каждой таблицы задаётся своё действие.

**`diff`**

1. Источник копируется через COPY с явным списком колонок в UNLOGGED staging `opsentri_sync_stage.stg_<job>_<n>` приёмника.
2. Затем одна транзакция приёмника:
   - проверка дубликатов ключа;
   - `DELETE` — только при `delete_missing`;
   - `UPDATE` строк, где хеш отличается;
   - `INSERT` новых строк.
3. Если у таблицы нет ключа: `INSERT … EXCEPT ALL`. При `delete_missing` лишние копии удаляются по `ctid` с помощью `row_number()`.
4. Staging удаляется в `finally`.

**`full`** — одна транзакция приёмника: `TRUNCATE` + `COPY FROM STDIN` с явным списком колонок.

**`create`** — существующий `ddl_check.create_missing_objects`, затем полная загрузка без TRUNCATE.

`compare_job_id` необязателен. Без него разрешено только `action='full'`, и таблица должна быть в обеих базах. Иначе item получает `skipped` с сообщением.

Фактические числа пишутся в сообщение item: `insert=N; update=M; delete=K` или `truncate+insert=N`. Статус `done` ставится только после коммита.

Стоп отменяет активный запрос или COPY и откатывает текущую таблицу. Задача получает `cancelled`, оставшиеся items — `skipped`.

Примитивы берутся из `modules/pg_sync_common.py` (таск 01, см. `interfaces.md`). Ключи и `expected` — из результатов сравнения (`pg_compare.get_results`), а не с клиента.

## Критерии приёмки

- [ ] `load_diff` с ключом:
  - DELETE выполняется только при `delete_missing=True`;
  - UPDATE затрагивает только строки с отличающимся хешем;
  - INSERT добавляет только новые ключи;
  - всё в одной транзакции;
  - дубликаты ключа в staging дают ошибку таблицы, а приёмник остаётся неизменным.
- [ ] `load_diff` без ключа: INSERT мультимножественной разности. При `delete_missing` удаляется ровно избыточная кратность.
- [ ] `load_full`:
  - TRUNCATE и COPY в одной транзакции;
  - при ошибке — rollback;
  - список колонок явный: порядок колонок в базах может отличаться.
- [ ] `create`: `create_missing_objects`, затем полная загрузка. Ошибка создания → item `failed` с текстом.
- [ ] Источник открыт read-only и не получает ни одной записи. Staging удаляется и при ошибке.
- [ ] Маршрут:
  - проверяет, что оба подключения postgres и src ≠ dst;
  - принимает только действия из списка;
  - для `diff` и `create` требует `compare_job_id` и таблицу из его результатов с подходящим статусом;
  - принимает `delete_missing` только как bool;
  - на ошибки валидации отвечает 400 с текстом по-русски;
  - защищён POLICY `sync.run`;
  - сохраняет в config `tables`, `expected`, `delete_missing`, `compare_job_id`, `source_connection_id`, `dest_connection_id`.
- [ ] Стоп:
  - `StopWatch` вызывает `conn.cancel()`;
  - выполняется rollback;
  - статусы `cancelled` / `skipped`;
  - закоммиченные таблицы остаются `done`.
- [ ] Тесты:
  - построители SQL, включая «без delete_missing нет DELETE»;
  - раннер на фейках: успех, ошибка таблицы, стоп;
  - маршрут: валидация и права;
  - весь набор зелёный.
