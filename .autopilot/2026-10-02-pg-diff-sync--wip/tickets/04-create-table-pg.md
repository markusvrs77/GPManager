## Что должно заработать

Слепая приёмка на живом PostgreSQL 17 показала, что действие `create` («создать и залить») падает всегда.

Цепочка такая:
- существующий `ddl_check.create_missing_objects` вызывает `fetch_object_ddl`;
- тот первым делом обращается к Greenplum-функции `pg_get_table_distributedby(oid)`;
- на PostgreSQL это `UndefinedFunction`, транзакция обрывается;
- item получает `failed` с текстом «current transaction is aborted».

`ddl_check` и `sync_transport` не трогаем (R04).

### Создание таблицы для PG↔PG

Таблица, которой нет в приёмнике, создаётся в `pg_diff_load` по каталогу PostgreSQL источника.

- **Транзакция.** Всё в одной транзакции приёмника: сначала `CREATE SCHEMA IF NOT EXISTS` (если схемы нет), затем `CREATE TABLE`.
- **Колонки.** В порядке attnum, тип через `format_type`, NOT NULL — как в источнике.
- **Первичный ключ.** Переносится из источника, если он там есть.
- **Generated-колонки.** Два допустимых варианта:
  - обычная колонка того же типа (значения придут из источника);
  - `GENERATED ALWAYS AS (выражение) STORED` по `pg_get_expr`.

  Выбранный вариант обоснуй одной строкой в CONCERNS.
- **Последовательности.** Ни default-ов на последовательности, ни identity: значения приходят из источника.
- **Партиционированный родитель.** Создаётся обычной таблицей, данные кладутся плоско. Это пометка в сообщении item, а не ошибка.
- **Безопасность.** Идентификаторы — только через `psycopg2.sql`. Источник читается в read-only сессии.
- **После создания.** Существующая полная загрузка с `require_empty=True`, затем `sync_sequences`.

Тексты сообщений item не меняются:
- `create+insert=N`;
- «создана в приёмнике; заливка не завершена»;
- «создана…, но заливка не прошла: …».

### Уборка висящего staging

Если процесс упал, таблицы `opsentri_sync_stage.stg_<job>_<n>` остаются.

При старте `run_pg_diff_load_job` удаляются висящие `stg_<job>_*` тех задач `pg_diff_load`, которые не в статусе `running` и не являются текущей задачей. Чужие объекты в схеме не трогаются. Ошибка уборки не валит задачу.

## Критерии приёмки

- [ ] `create` больше не вызывает `ddl_check.create_missing_objects`. Файлы `ddl_check.py` и `sync_transport.py` не изменены.
- [ ] Построитель DDL покрыт тестом по полному тексту SQL. Тестовая таблица содержит:
  - PK;
  - NOT NULL;
  - serial/identity — в приёмнике без default и без identity;
  - generated-колонку.
- [ ] Раннер на фейках:
  - `create` → создание → полная загрузка → итог `create+insert=N`;
  - ошибка создания → `failed` с текстом.
- [ ] **Живая проверка** на временном кластере: localhost:55432, пользователь `pgcheck`, trust, базы `src_db` и `dst_db`.

  2. Прогони путь `create` модуля напрямую из Python на реальных соединениях.
  3. Проверь, что в `dst_db` появилась таблица с PK и теми же строками, а `src_db` не изменилась.
  4. Удали созданные тобой объекты в обеих базах.
