# Спецификация: Postgres — сравнение двух баз и загрузка только разницы

## Задача

DBA держит две базы PostgreSQL (например, прод и тест) и хочет приводить приёмник к источнику, не перезаливая всё целиком.

Сейчас во вкладке Postgres Toolkit → «Синхронизация» есть только полная перезаливка через COPY. Не видно, чем базы отличаются, и нельзя догрузить только новые и изменённые строки.

## Решение

Во вкладке Postgres Toolkit → «Синхронизация» появляется второй режим: **«Сравнение и разница»**. Существующий режим «Перенос» остаётся как есть и открывается по умолчанию.

Сценарий нового режима:

1. Источник и приёмник берутся из тех же селекторов в шапке страницы.
2. Пользователь отмечает схемы целиком и/или отдельные таблицы.
3. Нажимает «Сравнить». Сравнение идёт фоновой задачей и ничего не меняет ни в одной базе.
4. По мере проверки строится таблица результатов. По каждой таблице в ней видно:
   - статус: совпадает, отличается, нет в приёмнике, нет в источнике, структура отличается, ошибка;
   - число строк в источнике и в приёмнике;
   - сколько строк будет добавлено, изменено и удалено.
5. Для каждой таблицы пользователь выбирает действие:
   - «разница»;
   - «полная (TRUNCATE + INSERT)»;
   - «создать и залить» — только для таблиц, которых нет в приёмнике;
   - «пропустить».
6. Нажимает «Загрузить» и подтверждает запуск в окне с итоговыми числами.
7. Загрузка идёт фоновой задачей, её можно остановить. Источник только читается. Каждая таблица в приёмнике меняется одной транзакцией: либо целиком, либо никак.

| 8 | R05i.1 | …результаты появляются по мере сравнения | Страница опрашивает сервер каждые 2–3 с, строки появляются по одной. Видно, какая таблица сравнивается сейчас |

| 10 | R03 | Как DBA, я гружу только разницу в таблицу с ключом | Действие «разница» вставляет строки с ключами, которых нет в приёмнике, и обновляет строки, где ключ совпал, а содержимое отличается. Совпадающие строки не трогаются |
| 11 | R03.1 | …ключ определяется сам | Ключ ищется по источнику в таком порядке: PK → уникальный индекс → сохранённый ключ (`sync_keys`). Найденный ключ и его происхождение видны в строке результата |

Без неё DELETE не выполняется. С ней удаляются строки с ключом, которого нет в источнике, а у таблиц без ключа — лишние копии строк |
| 14 | R06i.1 | …и источник никогда не меняется | Соединение с источником — только на чтение (read-only сессия). Все записи идут только в приёмник |
| 15 | R06i.2 | …и каждая таблица применяется атомарно | DELETE, UPDATE и INSERT по таблице выполняются одной транзакцией приёмника. Ошибка или стоп откатывают её, и таблица остаётся как была до загрузки |
| 16 | R06i.3 | …и дубликаты ключа не портят приёмник | Если ключ в источнике (в staging) не уникален, таблица получает статус «дубликаты ключа» и не загружается. Сравнение показывает это заранее как статус `duplicate_keys` |
| 17 | G01 | Как DBA, для таблицы я выбираю полную загрузку вместо разницы | «Полная (TRUNCATE + INSERT)» выполняет TRUNCATE и COPY всех строк источника в одной транзакции приёмника. При сбое данные приёмника остаются прежними |
| 17a | G01.1 | Как DBA, я делаю полную загрузку выбранного и без сравнения | Рядом с «Сравнить» есть кнопка «Полная загрузка (TRUNCATE + INSERT)». Она запускает `pg_diff_load` с `action='full'` для всех выбранных таблиц сразу, после подтверждения. Таблицы, которых нет в приёмнике, пропускаются с сообщением; создать их можно через сравнение и галку «создать и залить» |
| 18 | G02 | Как DBA, я создаю отсутствующую таблицу и заливаю её | У строки со статусом «нет в приёмнике» вместо выбора действия — отдельная галка «создать и залить», по умолчанию снята. Если её отметить, таблица создаётся по DDL источника через `create_missing_objects` и заливается целиком. Над таблицей результатов — галка «отметить все отсутствующие» |
| 19 | R07i | Как DBA, я останавливаю сравнение или загрузку | «Стоп» вызывает существующий `/api/jobs/<id>/stop`. Таблицы, закоммиченные до стопа, остаются `done` |
| 20 | R07i.1 | …и вижу задачи в истории | Задачи `pg_compare` и `pg_diff_load` видны в ленте «Запуски» Postgres Toolkit и в `/api/jobs/...` |
| 21 | R07i.2 | …и вижу итог по каждой таблице | Сообщение job_item — фактическое `insert=N; update=M; delete=K` или `truncate+insert=N`, либо текст ошибки. `done` ставится только после коммита |
| 22 | R03.3 | Как DBA, я вижу, если данные изменились между сравнением и загрузкой | Загрузка заново считает фактические числа. UI показывает рядом «ожидалось» (из сравнения) и «сделано» |
| 23 | R06i.4 | Как пользователь без права запуска синхронизации, я не могу запустить ни сравнение, ни загрузку | Старты требуют `sync.run`, чтение результатов — `sync.view`. Доступ к подключениям проверяется существующей проверкой доступа к кластерам |

## Решения по реализации

1. **Новый режим живёт рядом со старым, а не внутри шага «Как».** Код мастера «Что / Как / Когда» не меняется: новый режим — отдельная панель на той же странице и отдельный JS-файл. *Почему:* R04.

2. **Сравнение — по ключу и хешу строки.**
   - Обе сессии нормализуются одинаково: `DateStyle='ISO, YMD'`, `IntervalStyle='postgres'`, `TimeZone='UTC'`, `extra_float_digits=3`, `bytea_output='hex'`.
   - Хеш строки — `md5(ROW(<колонки, отсортированные по имени>)::text)`. Формат ROW отличает NULL от пустой строки.
   - Источник отдаёт `COPY (SELECT <ключ>::text..., <хеш> FROM ...) TO STDOUT`. Этот поток заливается во **временную** таблицу сессии приёмника.
   - Подсчёт выполняется в приёмнике, соединением временной таблицы с таблицей приёмника.
   - С ключом:
     - «добавить» — ключа нет в приёмнике;
     - «изменить» — ключ есть, но хеш другой;
     - «удалить» — ключа нет в источнике.
   - Без ключа:
     - «добавить» = `count(src EXCEPT ALL dst)`;
     - «удалить» = `count(dst EXCEPT ALL src)`.

   *Почему:* по сети идут только ключи и хеши, источник только читается, временная таблица живёт лишь в сессии приёмника. Нормализация сессий убирает расхождения в форматах дат между серверами.

3. **Загрузка разницы идёт через staging в приёмнике.**
   - Источник целиком копируется потоком COPY в UNLOGGED-таблицу `opsentri_sync_stage.stg_<job>_<n>` приёмника, с явным списком колонок.
   - Затем выполняется одна транзакция приёмника:
     1. проверка дубликатов ключа в staging;
     2. `DELETE` — только при `delete_missing`;
     3. `UPDATE ... WHERE хеш отличается`;
     4. `INSERT` новых строк.
   - Без ключа:
     - `INSERT ... SELECT FROM stage EXCEPT ALL SELECT FROM target`;
     - при `delete_missing` лишние копии строк удаляются по `ctid` (через `row_number()` в разрезе хеша).
   - Staging удаляется в `finally`.

   *Почему:* схема та же, что у существующей синхронизации Greenplum, но без бинарника gpcopy и без `DISTRIBUTED`. Приёмник меняется только на разницу.

4. **Полная загрузка** — одна транзакция приёмника: `TRUNCATE` + `COPY FROM STDIN` из потока источника с явным списком колонок. *Почему:* так требует G01 и атомарность. Существующий `copy_table_pipe` берёт `SELECT *`, а порядок колонок в двух базах может отличаться. Сам `copy_table_pipe` не меняется.

5. **Отсутствующие таблицы** создаются существующей `ddl_check.create_missing_objects(src_id, dst_id, [{schema, table}])`. Затем выполняется полная загрузка без TRUNCATE.

6. **Ключи** определяются по источнику существующими `table_catalog.fetch_primary_keys`, `fetch_unique_indexes`, `load_sync_keys` и `resolve_keys_hierarchy`. Новые читатели каталога не пишутся.

7. **Охват.**
   - Сравниваются обычные и партиционированные таблицы (`relkind` `r` и `p`). Вьюхи и матвьюхи не сравниваются.
   - Партиционированная таблица сравнивается на уровне родителя. Её листья исключаются из выбора (`drop_covered_partitions`).
   - Набор колонок сравнивается по именам, порядок не важен.

8. **Стоп.**
   - Раннер держит сторожевой поток. Раз в секунду он проверяет `is_stop_requested(job_id)` и при запросе вызывает `cancel()` у активных соединений.
   - Раннер ловит `QueryCanceledError` и откатывает приёмник.
   - Затем вызывает `mark_job_cancelled`, а оставшиеся items помечает `skipped`.
   - Маршрут `/api/jobs/<id>/stop` не меняется.

9. **Результаты сравнения** хранятся в новой SQLite-таблице `pg_compare_results`. Она создаётся в `init_db` через `CREATE TABLE IF NOT EXISTS`; существующие таблицы не меняются.
   - Колонки: `id`, `job_id`, `schema_name`, `table_name`, `status`, `key_columns_json`, `key_source`, `src_rows`, `dst_rows`, `to_insert`, `to_update`, `to_delete`, `message`, `compared_at`.
   - Статусы: `same | differs | no_dest | no_source | structure_diff | duplicate_keys | error | cancelled`.

10. **Задачи** создаются существующими `job_manager.create_job`, `create_job_items`, `mark_*`, `is_stop_requested`.
    - Типы: `pg_compare` и `pg_diff_load`.
    - В config есть `source_connection_id` и `dest_connection_id`, поэтому лента «Запуски» относит задачи к pg.
    - В `RESUMABLE_JOB_TYPES` эти типы не входят: оборванная транзакция и так откатилась.

11. **Права.** Новые эндпоинты вносятся в `POLICY`: старты — `sync.run`, чтение — `sync.view`. `test_web_auth_policy.py` остаётся зелёным.

12. **Безопасность SQL.**
    - Все идентификаторы передаются только через `psycopg2.sql.Identifier`.
    - Имена схем и таблиц сначала сверяются с каталогом источника.
    - Ключевые колонки должны существовать в обеих таблицах.

13. **Фронтенд.**
    - Новый файл `static/js/pg_compare.js`. Глобальные функции и id DOM в нём — с префиксом `pgcmp`.
    - Переключатель и панель в `gpcopy_pipeline.html` выводятся только внутри `{% if toolkit == 'pg' %}`.
    - В `gpcopy_pipeline.js` допустимо одно аддитивное изменение: добавить `pg_compare` и `pg_diff_load` в `RUN_TYPES` для pg и поднять `?v=`.
    - Используются существующие свои диалоги подтверждения (не `confirm()`) и визуальный язык страницы.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `modules/pg_sync_common.py` | общие примитивы PG↔PG | `open_pg(connection_id, readonly=False) -> conn` (проверяет `db_type=='postgres'`, нормализует сессию); `table_columns(conn, schema, table) -> [name,...]`; `row_hash_sql(alias, columns) -> sql.Composable`; `stream_copy(src_conn, dst_conn, select_sql, dst_table, dst_columns) -> rows`; `StopWatch(job_id, conns)` — контекст-менеджер, `.stopped` | SET нормализации, `os.pipe` + поток чтения, опрос стопа |
| `modules/pg_compare.py` | сравнение и его результаты | `expand_selection(src_conn, dst_conn, schemas, tables) -> [{schema, table, in_src, in_dst}]`; `compare_table(src_conn, dst_conn, schema, table, key_columns) -> {status, src_rows, dst_rows, to_insert, to_update, to_delete, message}`; `run_pg_compare_job(job_id)`; `save_result(job_id, row)`; `get_results(job_id) -> [dict]`; `latest_compare_job(src_id, dst_id) -> dict or None` | SQL сравнения, временную таблицу, резолв ключей |
| `modules/pg_diff_load.py` | применение | `load_diff(src_conn, dst_conn, schema, table, key_columns, delete_missing, stage_name) -> {insert, update, delete}`; `load_full(src_conn, dst_conn, schema, table, truncate) -> {rows}`; `run_pg_diff_load_job(job_id)` | staging, порядок DML, транзакции |
| `app.py` | HTTP-контракт | `POST /api/pg/compare/start` `{source_connection_id, dest_connection_id, schemas:[...], tables:[{schema,table}]}` → `{job_id}`; `GET /api/pg/compare/results?job_id=` → `{job, results}`; `GET /api/pg/compare/latest?source_connection_id=&dest_connection_id=` → `{job, results}` или `{job:null}`; `POST /api/pg/diff-load/start` `{source_connection_id, dest_connection_id, compare_job_id (необязателен; без него допустим только action='full'), delete_missing, tables:[{schema, table, action:'diff' or 'full' or 'create'}]}` → `{job_id}`. Дерево объектов — существующий маршрут каталога | валидацию, раскрытие выбора |
| `static/js/pg_compare.js` | UI режима | глобальные функции `pgcmp*` | состояние выбора, опрос |

Config задачи `pg_diff_load` содержит `tables` (с `action` и `key_columns` из результата сравнения), `expected` (`to_insert`/`to_update`/`to_delete` по таблице), `delete_missing` и `compare_job_id`.

**Швы для тестов:**
- SQL-построители `compare_table` и `load_diff` / `load_full` проверяются как чистые функции.
- Раннеры проверяются на фейковых соединениях и временной SQLite (по образцу `tests/test_copy_pipe_runner.py`).
- Маршруты проверяются через `client` из `tests/conftest.py`.

Живого PostgreSQL в тестах нет.
