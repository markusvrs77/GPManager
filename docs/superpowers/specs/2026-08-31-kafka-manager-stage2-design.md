# Kafka Manager, этап 2: консьюмер-группы и лаг

**Дата:** 2026-08-31
**Направление:** Data Flow → Kafka
**Статус:** утверждено, готово к планированию
**Предыдущий этап:** `2026-08-31-kafka-manager-stage1-design.md`

## Цель

Вкладка «Консьюмер-группы»: кто читает топики, в каком состоянии группы и
насколько они отстают. Плюс сброс оффсетов — к началу, к концу или на
дату — и удаление пустой группы.

## Условия

Те же, что на этапе 1: кластер PLAINTEXT, десятки топиков и групп, pip на
сервере есть, опасные операции разрешены с подтверждением и записью в
журнал. Автообновления нет: кластер опрашивается только по кнопке.

## Выбранный подход

Отдельная вкладка под Kafka со своим модулем и своим срезом в SQLite.

Отвергнуто:

- **третья карточка на вкладке «Обзор кластера»** — у групп свои фильтры,
  свой разворот по партициям и опасные действия; смешивать чтение
  метаданных с изменением оффсетов на одном экране не стоит;
- **считать лаг живьём при каждом открытии** — всегда актуально, но каждый
  заход бьёт по кластеру, а правило «только по кнопке» держим везде.

## Что умеет библиотека

Сверено по исходникам `kafka-python` 3.0.11, а не по памяти — на этапе 1
именно выдуманные имена полей стоили двух итераций.

| Метод | Отдаёт |
|-------|--------|
| `list_groups()` | список dict: `group_id`, `protocol_type`, `group_state` |
| `describe_groups(ids)` | `{group_id: {...}}`: `group_id`, `group_state`, `protocol_type`, `protocol_data`, `members[]` |
| `describe_groups` → member | `member_id`, `group_instance_id`, `client_id`, `client_host`, `member_metadata`, `member_assignment` |
| `list_group_offsets({gid: None})` | `{group_id: {TopicPartition: OffsetAndMetadata}}` |
| `reset_group_offsets(gid, specs)` | `{TopicPartition: {'error': ...}}` |
| `delete_groups(ids)` | результат по каждой группе |

`OffsetSpec` — целочисленные константы: `EARLIEST = -2`, `LATEST = -1`.
Для даты передаётся `OffsetTimestamp` — миллисекунды эпохи; брокер сам
находит первый оффсет с временем `>=` указанного.

Концы партиций уже умеет `modules/kafka_client.fetch_offsets` с этапа 1.

## Данные

Новая таблица рядом с `kafka_snapshots`, создаётся в `db.init_db()`:

```sql
CREATE TABLE IF NOT EXISTS kafka_group_snapshots (
    cluster_id INTEGER PRIMARY KEY,
    taken_at TEXT NOT NULL,
    payload BLOB NOT NULL,
    groups_total INTEGER NOT NULL DEFAULT 0
);
```

`payload` — `zlib(json)`, как у среза обзора. Журнал действий пишется в
`kafka_audit`, заведённую на этапе 1 и до сих пор пустую.

`modules/kafka_clusters.delete_cluster` сейчас чистит только `kafka_snapshots`;
в этом этапе он должен удалять и групповой срез, иначе после удаления
кластера в базе останется сирота. Записи `kafka_audit` при этом сохраняются:
журнал должен переживать объект, к которому относится.

Даты — строки `YYYY-MM-DD HH:MM:SS`.

### Формат среза

```json
{
  "groups": [
    {
      "id": "etl-loader",
      "state": "Stable",
      "protocol": "range",
      "members": 3,
      "partitions": 6,
      "lag": 12045,
      "topics": [
        {
          "name": "orders",
          "lag": 12045,
          "parts": [
            {"p": 0, "committed": 4100, "end": 9000, "lag": 4900,
             "client": "c-1", "host": "10.0.0.7"}
          ]
        }
      ]
    }
  ]
}
```

Партиция без закоммиченного оффсета получает `committed: null` и
`lag: null`. В интерфейсе это прочерк, а не ноль: «отставания нет» и «ни
разу не читали» — разные вещи, и путать их нельзя.

Суммарный лаг группы и топика считается только по партициям с известным
лагом; если известных нет, лаг группы тоже `null`.

## Модули

### `modules/kafka_groups.py`

- `build_groups(groups_meta, committed, end_offsets)` — **чистая функция**:
  описания групп, `{(group, topic, partition): committed}` и
  `{(topic, partition): end}` → структура среза выше. Тестируется без
  брокера.
- `collect_groups(cluster_id, force=False)` — без `force` отдаёт срез из
  базы, с `force` опрашивает кластер и сохраняет.
- `load_snapshot` / `save_snapshot` / `empty_groups` — по образцу
  `modules/kafka_overview.py`.
- `build_reset_specs(mode, target, partitions)` — **чистая функция**:
  режим (`earliest`, `latest`, `timestamp`), значение и список партиций →
  словарь для `reset_group_offsets`. Отдельно, потому что это единственное
  место, где легко ошибиться в границах.
- `GroupBusy(Exception)` — объявляется здесь же;
- `assert_group_is_idle(group)` — поднимает `GroupBusy` с человеческим
  текстом, если у группы есть активные участники. Роут ловит её
  и отвечает 409.

### `modules/kafka_client.py`

Добавляются, оставаясь единственным местом с `import kafka`:

- `fetch_groups(cluster)` → `(list_groups, describe_groups)` сырыми
  структурами;
- `fetch_group_offsets(cluster, group_ids)` → `{(group, topic, partition):
  committed}`;
- `reset_offsets(cluster, group_id, specs)` → результат по партициям;
- `delete_group(cluster, group_id)`.

Ключи наружу — кортежи строк и чисел, `TopicPartition` за границу модуля
не выходит.

### `modules/kafka_audit.py`

- `write(cluster_id, action, target, details, result)` и
  `recent(cluster_id, limit=50)`. Таблица есть с этапа 1, кода к ней ещё
  нет.

### `kafka_routes.py`

Добавляются в существующий Blueprint:

| Метод | Путь | Назначение |
|-------|------|-----------|
| GET | `/kafka/groups` | страница |
| GET | `/api/kafka/clusters/<id>/groups` | срез из БД |
| POST | `/api/kafka/clusters/<id>/groups/refresh` | опросить кластер |
| POST | `/api/kafka/clusters/<id>/groups/<gid>/reset` | сброс оффсетов |
| DELETE | `/api/kafka/clusters/<id>/groups/<gid>` | удалить группу |
| GET | `/api/kafka/clusters/<id>/audit` | журнал действий |

Тело сброса: `{"mode": "earliest|latest|timestamp", "timestamp":
"2026-08-30 00:00", "topics": ["orders"]}`. Пустой `topics` — вся группа.

## Экран

`templates/kafka_groups.html` + `static/js/kafka_groups.js`, стиль как у
двух готовых вкладок. В меню — третий пункт «Консьюмер-группы».

Шапка: выбор кластера, бейдж «срез от …», кнопка «Обновить срез».

Список групп: имя, состояние, участников, партиций, суммарный лаг.
Сортировка по лагу по убыванию — сверху то, что отстаёт сильнее.
Фильтр по имени и галка «только с лагом». Строка разворачивается в топики
и партиции: закоммичено, конец, лаг, клиент и хост участника. Разворот
обёрнут в `window.gpKeepScroll`.

Внизу вкладки — журнал последних действий из `kafka_audit`.

## Опасные действия

Сброс оффсетов и удаление группы доступны только у группы без активных
участников — так требует сама Kafka. Состояние проверяется **до** запроса
к брокеру: если участники есть, возвращается 409 и текст «В группе 3
активных участника, остановите потребителей и повторите», а не глухая
ошибка из библиотеки.

Подтверждение — вводом имени группы, как при пересоздании таблиц в
синхронизации (`gpConfirm`). Диалог сброса показывает, что именно
поменяется: режим, охваченные топики и число партиций.

Дата для режима `timestamp` вводится календарём с часами и минутами —
тем же способом, что в расписаниях, — и переводится в миллисекунды эпохи.

Каждое действие пишется в `kafka_audit` до и после выполнения: сначала
намерение, затем результат по партициям. Если часть партиций не
сбросилась, ответ содержит список неудачных и общий статус «частично».

## Ошибки

| Ситуация | Поведение |
|----------|-----------|
| Библиотеки нет | Страница открывается, баннер с командой установки, кнопки обновления и действий заблокированы. |
| Кластер недоступен | 502 и красный баннер; прежний срез остаётся на экране. |
| В группе есть участники | 409 с числом участников; действие не выполняется. |
| Группа исчезла между срезом и действием | 404 «Группа не найдена — обновите срез». |
| Часть партиций не сбросилась | 200 со статусом «частично» и списком партиций с ошибками; в журнал пишется тот же список. |

## Тесты

Без брокера, на чистых функциях и подменах:

1. `build_groups`: суммирование лага по топику и группе; партиция без
   коммита даёт `null`, а не ноль; группа без единого коммита получает
   `lag: null`; имена полей берутся из реальных схем `kafka-python` 3.x
   (`group_id`, `group_state`, `members`, `client_id`, `client_host`).
2. `build_reset_specs`: три режима дают `-2`, `-1` и миллисекунды;
   пустой список партиций отвергается.
3. `assert_group_is_idle`: `Stable` с участниками — отказ, `Empty` —
   проходит.
4. Снапшот-слой: сохранение и чтение, пустой срез, удаление кластера
   чистит и групповой срез.
5. `modules/kafka_audit`: запись и чтение последних записей, порядок от
   новых к старым.
6. Роуты через `flask.test_client`: срез, `refresh` с `force=True`,
   сброс на активной группе даёт 409, успешный сброс пишет в журнал,
   недоступный кластер даёт 502.
